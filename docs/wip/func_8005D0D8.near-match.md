## What it is

`func_8005AF50()` returns a `u8*` game-state base. 5 entries at `base + 0x1DF0 + i*0x68`.
Loop A zeros `s32 flags[5]`. Loop B flags entry `i` if any validation fails: `(byte36 & 0x80)` with
`(byte36 & 0xF)` outside `[0,4]`, or `byte37 >= 0x12`, or `byte39 >= 4`, or `byte34 >= 6`, or
`byte35 >= 6`. Loop C toggles bit 7 of byte 0x36 on each flagged entry.

## The four levers that closed the 6-instruction deficit (S315)

1. **Separate range tests, not `||`** — `if (lo >= 5) f; else if (lo < 0) f;`. The S264/S272 verdict
   ("combine proves `lo = b & 0xF >= 0` locally and drops the dead `bltzl`, source-invariant") named
   the wrong pass: `lo >= 5 || lo < 0` is merged at *tree* level by `fold_range_test` into one
   `(unsigned)lo >= 5`, which is the single `sltiu` every S272 variant produced. Written as two tests
   the ROM's `slti` + `bltzl` pair comes back unchanged. See the memory
   `gcc272-fold-range-test-slti-merge` (a per-test split defeats the merge).
2. **`s32 v = p[0x36]; v ^= -0x80; p[0x36] = v;`** — an explicit `s32` temp makes the xor SImode, so
   `-0x80` will not fit `xori`, has to be materialised in a register, and `loop.c` then hoists it as
   the ROM's `li t0,-0x80` in the preheader. The S264 verdict ("gcc drops the high bits pre-loop
   motion, not reproducible") holds only for the compound form `p[0x36] ^= -0x80` on a `u8` lvalue,
   which expand narrows to QImode.
3. **No explicit `off` / `fp` variables — index everything off `i`.** The ROM's loop preheaders are
   ordered `i = 0`, hoisted constants, *then* the pointer inits, which is only possible if the
   pointers are `loop.c` givs: source statements are emitted before the hoists, giv inits after them.
   Writing `off`/`fp` as real variables put their inits first (wrong order) and, with `flags[i]` also
   present, let `loop.c` eliminate the `i` biv entirely against the flags pointer, costing the
   counter, its bound constant and its increment. Spell the address `base + (0x1DF0 + i * 0x68)` —
   the parenthesised part is the giv, so `base` is added inside the loop as the ROM's
   `addu a0,t1,t0` (memory `fold-associate-constant-side`).
4. **`s8 lo`, not `s32 lo`.** With `s32` the copy `lo = b` is propagated by `cse` into the mask
   (`andi v1,v0,0xF` straight off the `lb` result) and the copy dies. Declared `s8`, the copy
   survives as the ROM's `move v1,v0` plus the in-place `andi v1,v1,0xF`, and gcc additionally
   reserves the 8 frame bytes that take the frame from `-0x30` to the ROM's `-0x38`. One edit, two
   residuals. `flags[8]` also reaches `-0x38` on its own but over-reserves once `s8 lo` is in;
   `flags[5]` + `s8 lo` is the pair that matches.

## Residual (S315): a three-register rotation

Instruction stream and frame are exact. The only diff rows are register names:

| role | ROM | build |
| --- | --- | --- |
| counter `i` (one variable, all three loops) | `a1` | `a2` |
| loop-B flags giv | `a2` | `a0` |
| loop-B entry pointer `p` | `a0` | `a1` |
| loop-C flags giv | `a2` | `a1` |

Everything else (`t0` off-giv, `t1` base, `t2`/`a3` constants, `v0`/`v1`) already matches, and the
loop-C `off` giv is `a0` on both sides. The whole table follows from one decision: which of the three
is allocated first.

`venv/bin/python3 tools/allocno_report.py src/main/func_80059BA0.c func_8005D0D8` on the 67/67 body:

| allocno | role | refs | len | priority | reg |
| --- | --- | --- | --- | --- | --- |
| 169 | loop-B flags giv | 17 | 35 | 19428 | `a0` |
| 78 | loop-B entry pointer | 12 | 26 | 13846 | `a1` |
| 73 | counter `i` | 21 | 61 | 13770 | `a2` |

The build's order is {flags giv, `p`, `i`}; the ROM's is {`p`, `i`, flags giv}. `p` above `i` already
matches, so the single thing to change is the flags giv dropping from first to last, i.e. its
priority below 13770. `floor_log2(refs)*refs/live_length` (`global.c:587`) puts the boundary at
`refs <= 15` (the `floor_log2` step at 16 does the work: `3*15/35 = 1286`) or `live_length >= 50`.

The ref counts are `flow.c`'s loop-depth-weighted ones: an in-loop reference counts 2, a preheader
reference 1. So the flags giv's 17 is `1 (giv init) + 2 * (6 stores + 2 for the increment)`, `p`'s 12
is `2 * (1 set + 5 loads)`, and `i`'s 21 is `3 inits + 2 * 3 loops * (increment 2 + compare 1)`.
Every one of those counts is forced by the ROM's own instruction stream, which is why no reweighting
edit was found: removing a flags-giv reference means removing one of the six stores.

## Refuted this sprint (S315)

- `s32* f = &flags[i];` as a block-scoped record pointer: identical giv, identical allocation.
- `flags[6]` / `flags[7]` / `flags[8]` with `s8 lo`: `-0x38`, `-0x40`, `-0x40`; only `flags[5]` fits.
- Re-reading the byte inside the guard (`s32 lo = *(s8*)(p + 0x36);`) instead of copying `b`: no
  `move`, same 66/67.
- Permuter, 11108 iterations at `-j6`, seed 4242: base score 155, never improved, no candidate
  written. This is the multi-register permutation shape the oracles table says plateaus.

## Historical: the S264/S272 residual framing (all three since refuted)

1. bit7 `lo < 0` range-elimination coin (~2 instr), called a combine global-vs-local `nonzero_bits`
   choice and "source-invariant". It was `fold_range_test`; lever 1 fixes it.
2. xor-hoist coin (1 instr), called "not reproducible while gcc simplifies the constant to fit
   `xori`". Lever 2 fixes it.
3. base-register allocno, called "not source-steerable here". Levers 3 and 4 fixed the register
   *count* and the frame; a three-register rotation remains, now measured rather than asserted.

The S264 levers that did land and are superseded rather than wrong: the up-count pointer walk in
loop A (`*fp++`, `++i != 5`) and the `p = base + off` placement outside the loop-C `if` both produce
the ROM's shapes, but the giv form in lever 3 produces them without the explicit variables.
