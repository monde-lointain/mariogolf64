# func_80065A1C near-match — mechanism confirmed, allocation residual left

`void func_80065A1C(f32* mf, f32* angles, f32* pos)` (0x80065A1C, 0x17C) in
`src/main/set_camera_matrices_fixed.c` (`main/set_camera_matrices_fixed` bank).
Six `sinf`/`cosf` calls over the three angles, then a fixed multiply/add chain
writing a 4x4 matrix.

## Mechanism — dump-cited (responsible pass: global-alloc)

Command (isolated candidate, parent profile; KMC gcc writes the dump at the
repository root named after the input basename, then it was moved into the
candidate directory):

```sh
uv run --locked python tools/rom_build.py compile \
  --source nonmatchings/func_80065A1C/base.c --output nonmatchings/func_80065A1C/diagnostic.s \
  --profile-source src/main/set_camera_matrices_fixed.c --nonmatching --assembly-only --extra-flag=-dg
```

Dump: `nonmatchings/func_80065A1C/base.c.greg` (seed version). It shows the FP
allocations landing in `$f0..$f18` plus **five** callee-saved registers:

```
;; Hard regs used: 4 5 6 16 17 18 31 32 34 36 38 40 42 44 46 48 50 52 54 56 58 60
```

(32/34/…/60 = `$f0,$f2,…,$f28`; **62 = `$f30` is absent**), i.e. frame `0x48` — the
ROM's frame is `0x50` with six `sdc1` pairs `$f30..$f20`.

**Mechanism:** a value gets a callee-saved FP register only if its allocno is live
across a call. The ROM's sixth register holds the `m->4` product
`cosf(angles[1]) * sinf(angles[2])` (`mul.s $f30,$f22,$f20` at 0x90, stored at 0x108),
so in the ROM's source that product is formed **between the fifth trig call
(`sinf(angles[2])`) and the sixth (`cosf(angles[2])`)** — the scheduler later sinks
the multiply into the multiply block.

**Falsifiable prediction + result:** naming that product in a temp declared at that
point makes the allocno live across the last call and should pull in `$f30`.
Implemented (`temp_ft3 = temp_fs1 * temp_fs0;` after `temp_fs0 = sinf(angles[2]);`,
stored later at `m+0x4`) and the prologue/epilogue now match the ROM **exactly**:

```
0000 addiu sp,sp,-80
0018 sdc1 $f30,72(sp)  001c sdc1 $f28,64(sp)  0020 sdc1 $f26,56(sp)
0024 sdc1 $f24,48(sp)  0028 sdc1 $f22,40(sp)  002c sdc1 $f20,32(sp)
...
0158-0170 ldc1 $f30..$f20      0174 jr ra      0178 addiu sp,sp,80
```

Measured: `match_count` 52/97 → **60/98**, score 975 → 1010 (rows 98 vs ROM 95).

## Remaining residual

- The first two trig results are swapped: ROM `sinf(a0)→f28`, `cosf(a0)→f26`; the
  build assigns the other way round, which cascades through the multiply chain's
  operand registers.
- One extra `mov.s` in the build (`mov.s $f22,$f0` after the fifth call) and one
  instruction fewer overall; the `m->4` multiply stays beside the call instead of
  being scheduled into the multiply block.

copies, not a re-weighting.
