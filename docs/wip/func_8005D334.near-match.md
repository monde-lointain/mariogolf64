# func_8005D334 near-match (S210 compiler-source dive)

**Status:** STRUCTURAL BYTE-MATCH achieved; residual = one regalloc-pressure

## What it is
Zeroes an array of 4 structs (size 0x16) based at `D_800FE3D8`. Each struct:
`s16 a,b,c,d` (0x00..0x07) + `u8 e[12]` (0x08..0x13) + `u8 f` (0x14), 1 pad
byte. ROM uses THREE induction vars: outer counter `a2` (0..3, `bne a2,4`),
byte-offset `v1` (0,22,44,66 -> `%hi/%lo(field)+v1` direct-index for the 4
halfwords + trailing byte), and a walking pointer `a0` (`&D_800FE3E0`, advanced
+22) for the inner 12-byte up-pointer loop.

## Working source (structural match, middle byte-identical)
```c
typedef struct { s16 a,b,c,d; u8 e[12]; u8 f; } St;   /* 0x16 */
extern St D_800FE3D8[4];
void func_8005D334(void){
  s32 i, n; u8 *row, *p, *end;
  row = D_800FE3D8[0].e; n = 12; i = 0;
  do {
    D_800FE3D8[i].a=0; D_800FE3D8[i].b=0; D_800FE3D8[i].c=0; D_800FE3D8[i].d=0;
    p = row; end = row + n;
    do { *p = 0; p++; } while (p != end);
    D_800FE3D8[i].f = 0;
    row += 22;
  } while (++i != 4);
}
```
Levers that got it here (all confirmed via `gcc -S` oracle + in-tree diff):
1. **Walking pointer `row` for the inner array** -> the counter `i` SURVIVES
   (3-IV structure). Without it, loop.c merges the counter into the offset giv
   and tests `offset < 88` (2-IV). This is THE key structural lever.
2. **Inner loop as up-pointer `do{*p=0;p++}while(p!=end)`** -> ROM's up-pointer
   `bnel v0,a1`. A `for(j=0;j<12;j++)` reverses to a down-counter (loop.c biv
   reversal).
3. **`end = row + n` with `n` a variable** -> keeps 12 in a REGISTER (ROM's
   `addu a1,a3,a0`, a3=12). Literal 12 emits `addiu` immediate.
4. **`do/while(++i != 4)`** -> the ROM's `!= 4` (bne), not `< 4` (slt).

## Residual (the wall) + root cause
Middle ~20 instrs byte-identical. The ONLY diffs cascade from ONE decision:
my build HOISTS the exit constant `4` into a dedicated hard register (`a3`),
the ROM REMATERIALIZES it inline (`li v0,4` reusing the inner scratch v0).
This pushes 12 to `t0`(=$8) instead of `a3`, flips the `addu` operand order,
and swaps the bne-delay-slot fill (row++ vs offset++).

Root cause (gcc-2.7.2 source):
- `config/mips/mips.c:1996-1997` (`gen_int_relational` path): an `==`/`!=`
  compare vs a NON-ZERO const `force_reg`s the const at EXPAND time -> creates a
  hoistable `set pseudo,4`. So EVERY `!= 4` source produces a hoistable li.
- `loop.c:1630` (`move_movables`): hoists it whenever
  `threshold*savings*lifetime >= insn_count`; `threshold = 2*(1+n_non_fixed_regs)`
  is huge -> ALWAYS hoisted. So the li-4 is always moved before the loop.
- Whether the hoisted `4`-pseudo KEEPS a hard reg (mine) or gets rematerialized
  by reload (ROM) is a REGISTER-PRESSURE / allocno decision. Both `4` and `n`(12)
  are global.c priority-0 (n_refs=1 -> floor_log2(1)=0), so the a3 assignment is
  an allocno-number tie-break. Mine uses 7 regs (dedicated $7 for 4); ROM uses 6
  + rematerialize. Need +1 pressure OR to flip the 4/12 allocno tie so 12 wins a3
  and 4 loses -> rematerializes.
