# `func_800947A8` near-match (S301)

`src/main/func_8008D100.c`, 618 instructions, 0x9A8. Sky-panel snapshot emitter, sibling of the
banked `emit_snapshot_panel_grid_dl` in the same file.

## Status

**Exact instruction count (618/618), exact frame (-0x98), fully reconstructed semantics.** Not
banked. `cmpfn` diff is 404 lines (about 200 of 618 instructions differ), all downstream of one
`loop.c` movable-selection coin.

## What the function does

`n = D_800C5EE4`, early-out if `n <= 0`. Builds one modelview matrix from
`func_80065A1C(mf, angles, pos)` + `convert_and_pack_floats_to_fixed(mf, &D_800E4BD0[bank])` with
`angles[0] = 0`, `angles[1] = angles[2] = (f32)(D_800D1E50 - n * D_800D1E48)`,
`pos = {0, 0, -290.0f - (f32)(0xFF - n)}`. Then an 18-command DL preamble, a 4x5 textured-quad grid
(`gDPLoadTextureBlock` 64x32 RGBA16 + 4 `gSPModifyVertex(G_MWO_POINT_ST)` + `gSP2Triangles`), a
second 4x5 `gSP2Triangles`-only pass under `G_CC_SHADE`, a 24-vertex reload, a 3x5 pass with a
different ST layout, and `D_800C5EE4 -= 10`.

Vertex indices per cell are `k = j + row`, `k+6`, `k+7`, `k+1`, where `row`/`row1` are loop-carried
accumulators stepping by 6 per outer iteration, copied into per-outer temps (`base`, `base1`) at the
top of the outer body. Last column (`j == 4`) narrows the S coordinate from `0x40` to `0x2F`.

## The coin, quantified (loop.c:1631)

`move_movables` moves an invariant when

```
already_moved[regno] || (threshold * savings * m->lifetime) >= insn_count
```

with `threshold = (loop_has_call ? 1 : 2) * (1 + n_non_fixed_regs)` (loop.c:532) and
`threshold -= 3` after every move (loop.c:1719 and 1904). For this target `n_non_fixed_regs` is 60,
so **threshold starts at 122 and steps down by 3 per move**. `savings = n_times_used[regno]`, which
is a copy of `n_times_set` (loop.c:597, 793) -- the number of *sets* in the loop, so a
materialise-once constant has `savings == 1`, and `lifetime` for a constant fed straight into a
`bne` is 1 (def and use are adjacent by construction of RTL expansion).

So for the life-1 constants the window is a pure function of the loop's RTL insn count:

```
moves = floor((122 - insn_count) / 3) + 1
```

Verified on both loops of this build: loop 1's inner loop is `115 real insns` -> 122, 119, 116 all
pass and 113 fails, giving exactly **3** life-1 moves; loop 3's inner loop is `117 real insns` ->
122, 119 pass and 116 fails, giving exactly **2**. Both match the `-dL` dump.

Decoded, the movable list for loop 1's inner loop (`Loop from 473 to 851: 115 real insns`) is:

| insn | regno | const | life | outcome |
| --- | --- | --- | --- | --- |
| 494 | 211 | `0xFD100000` SetTextureImage | 1 | moved (threshold 122) |
| 506 | 217 | `-8` mask | 1 | moved (119) |
| 521 | 221 | `0xF5100000` SetTile | 1 | moved (116) |
| 525 | 222 | `0x07000000` | 1 | **not desirable** (113 < 115) |
| 574 | 235 | `0xE7000000` PipeSync | 104 | moved (long life) |
| 626 | 245 | **`4`** | 1 | **not desirable** (113 < 115) |
| 677 | 253 | `0x02140000` MODIFYVTX | 31 | moved (long life) |
| 704 | 262 | `0x400` | 1 | not desirable |
| 800 | 303 | `0x06000000` TRI2 | 1 | not desirable |

The ROM's set is `{0xFD100000, -8, 4}` plus the same two long-life ones. So the ROM's list must have
the `4` movable ahead of `0xF5100000`, or the `4` must carry `savings * lifetime >= 2`. Neither is
reachable from this source shape:

- **Order.** The movable list is built in scan order from `scan_start` with a wrap-around (the
  trailing `Insn 476` entry is the wrap). `0xF5100000` is the second word of
  `gDPLoadTextureBlock`, and the `j == 4` branch cannot be spliced between the block's first and
  second store because a branch ends the basic block and the ROM's seven texture-block stores all
  precede the `bne`. Moving the `w`-select ahead of the block *does* land `s6 = 4` (confirmed) but
  drags the branch and the four index computes to the top of the body: 560.
- **`savings`.** It counts sets, not uses, so sharing the constant with the outer `i != 4` bound
  cannot raise it. `combine_movables` (loop.c:1283) does add savings for two movables loading the
  same constant, but the inner-loop scan contains only one `4`; the outer scan sees both and
  records `savings 2`, by which point `insn_count` has been doubled once per already-moved reg
  (loop.c:1611) to `123 * 2^5`, so it fails there.
- **`lifetime`.** RTL expansion emits `(set r 4)` immediately before the `bne`, so no source form
  puts an insn between them without also changing the emitted instruction count (`if (tl == base +
  4)` costs an extra `addiu`).

Making the `4` a real variable (`last = 4`) does hoist it -- `s6 = 4` lands -- but it stops being a
movable, so the count of global allocnos goes to eight for seven callee-saved registers and reload
re-materialises both `0xFD100000` and `0xF5100000`: 594.

## Next actions

**S302 correction: action 1 below, as S301 wrote it, cannot work.** Re-measured on the committed
body with `tools/loop_window.py`, loop 1's inner loop is **117 real insns** (not 115) and the moved
set is already the ROM's minus the `4`: `0xFD100000` at threshold 122, `-8` at 119, `0xE7000000`
(life 102) at 116 -> 113, `0x02140000` (life 33) after the `4`. `0xF5100000` is *not* moved here
either, so the register table above is stale on that row -- the two builds differ only in the `4`.

The `4` is reached at **threshold 113 against insn_count 117**, so it needs
`savings * lifetime >= 2`, and lowering `insn_count` is the wrong direction:

| insn_count | what moves before the `4` | threshold at the `4` | verdict |
| --- | --- | --- | --- |
| 117 (now) | FD10, -8, E700 | 113 | 113 < 117, needs `savings*lifetime >= 2` |
| 113 | FD10, -8, F510, E700 | 110 | still fails |
| 110 | FD10, -8, F510, 0x07000000, E700 | 107 | still fails |
| <= 107 | the five above | 107 | passes, but F510 and 0x07000000 are now hoisted too, so the register set is wrong anyway |

Every extra life-1 slot a smaller loop opens is consumed by a movable that is scanned *ahead* of the
`4`, and each one costs another 3 of threshold. So the ROM cannot be reproduced by shrinking the
loop. The ROM's `4` must carry `savings >= 2` or `lifetime >= 2`, and the ROM's own register table
says how: its `$s6` serves both the inner `j == 4` test and the outer `i != 4` bound, i.e. **one
pseudo**, whose `REG_LIVE_LENGTH` is therefore function-wide rather than 1. In this build the two
are separate pseudos with life 1 each, and the merge only happens in the outer scan, where
`insn_count` has already been doubled per already-moved reg (loop.c:1611).

1. So the open question is narrower than S301 stated: **make the inner `j == 4` test and the outer
   `i != 4` bound share one pseudo before `loop.c` runs.** `s32 last = 4;` does it at source level
   but cprop re-materialises both (measured 594-887). Candidates not yet tried: an outer loop form
   that emits its bound test ahead of the inner loop (a `goto` outer loop keeps the test where it is
   written, at the cost of the outer loop's strength reduction, which currently produces the
   `row`/`row1` givs), or any spelling that leaves `4` in a register cse will reuse across the inner
   loop's back edge.
2. Removing the `do { } while (0)` around the `j == 4` test does not change the `4`'s life or
   savings (still 1/1), so the S301 ref-doubling lever and this coin are independent.
3. Do not price this leaf as fresh at the next gate: it is a characterised carry.
