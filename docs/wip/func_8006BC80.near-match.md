## What it does

icons. `D_800C4124` is a five-state phase (-1 off, 0 winding in, 1 held,
3 winding out, 4 done) and `D_800C4120` the 0..4 wind counter. The banner is two
stacked 256x32 CI4 rectangles centred on x=160, scaled by the wind counter; at
full extent two 72x24 CI8 icons are drawn at x=128 and x=192, wobbling on
`sinf(D_800C412C)` with `D_800C412C` advanced 20 degrees per frame.

All 17 display-list words decode to plain SDK macros (`gDPPipeSync`,
`gDPSetTextureLUT/Filter/Persp`, `gDPSetPrimColor/EnvColor`,
`gDPSetRenderMode(G_RM_CLD_SURF, …)` / `(G_RM_TEX_EDGE, …)`,
`gDPSetCombineMode(G_CC_BLENDPEDECALA…)` / `(G_CC_DECALRGBA…)`) — no raw command
words are needed and every constant word is reproduced bit-exactly.
`func_8006A2C0` is a `gSPScisTextureRectangle` emitter taking 10 arguments
(verified from its own `.s`: E7 pipesync, E4 texrect, E1/F1 rdphalf, E7).

## Finding 1 — the loop's 62nd RTL insn (loop.c:1631, exact arithmetic)

The natural body compiles with a ninth saved register (`s7`) holding a hoisted
constant `1`, the operand of the loop-top `D_800C4124 == 1` test.
`gcc-2.7.2/loop.c` `move_movables` hoists a loop-invariant when

```
threshold * savings * m->lifetime >= insn_count          loop.c:1631
threshold = (loop_has_call ? 1 : 2) * (1 + n_non_fixed_regs)   loop.c:532
```

Here `savings = lifetime = 1` and, from the `-dL` dump, `threshold` is exactly
61: with a 61-insn loop the `li 1` moves, with a 62-insn loop it prints
"not desirable". It is the FIRST movable scanned, so it sees the undecremented
threshold; every later life-1 movable in the same loop (`2`, `160`, `0x20000`,
`0x8000`, `32`) is already past `threshold -= 3` (loop.c:1719) and is refused —
which is why only this one constant was hoisted.

So the ROM's loop body carries one more RTL insn than the natural spelling, and
that insn produces **no** final instruction (the two loops are otherwise
instruction-for-instruction identical). It therefore dies in `flow` after `loop`.
At the time this was found, any single dead assignment at the loop top
reproduced it — `y = 0`, `hgt = 0`, `halfw = 0`, `yc = 0`, `y = i`, or a dead
store inside the then-arm. (By the final body this is no longer true: with the
Finding 5 change in place the slot is `yc = 0;` specifically, and `hgt = 0`
there gives 476 instructions — `yc`'s own reference count now matters too.)

**What the ROM source actually writes there is not recoverable from the asm**,
because `flow` deletes it before final and it emits no instruction. The
`yc = 0;` in `base.c` is therefore a PLACEHOLDER FOR AN UNKNOWN SOURCE
STATEMENT, not a reverse-engineered one — it reproduces the ROM's instruction
stream without any claim to be what the original author wrote. A later reader
should not promote it to RE'd truth; if the real statement is ever recovered
from a sibling function or a symbol, it should replace this line. Everything
else in the body is derived from the `.s`; this one line is not.

The giv spelling `(u32)D_800E1C08 + 8 + off` (with `off` from 0) also reaches 62
insns, but loop.c refuses to strength-reduce it — `giv of insn 469 not worth
while, 0 vs 62` — so the `+8` survives as a live `addiu` and the `off` biv is
never formed. Not usable.

## Finding 2 — the frame's 8 dead bytes are a block-scoped decl

ROM's frame is 0x70; the natural body's is 0x68. Saved registers are the same
eight (`s0`-`s6`, `ra`, 0x50..0x6C), so ROM's vars region is 0x38..0x4F = 24
bytes for 12 bytes of live locals: `sp38`/`sp3C` (the `func_8007399C`
out-params) at 0x38/0x3C and `gfx` at 0x40.

Stack slots are handed out in **first-address-taken order**, not declaration
order — verified by moving the `Gfx* gfx` declaration (no effect) and by growing
the out-param pair into an array (`gfx` moved to 0x48). `&gfx` is first taken
inside the loop, so anything sitting above 0x40 must be declared in a block
entered *after* the loop. `s32 unused[2];` at the top of the trailing
`if (D_800C4124 == 1)` block reproduces the frame exactly; `unused[3]`/`[4]`
overshoot to 0x78 and an `f64` slot undershoots to 0x68.

## Finding 3 — one variable per region, not one per role

The single largest fix. `ulx`, `uly` and `yc` were each assigned once in the
x=0x80 rectangle block and once in the x=0xC0 block. One variable carrying two
values is exactly the anti-dependency of `one-variable-reuse-reorders-loads`:
giving the second block its own `ulx2`/`uly2`/`yc2`/`yc3` collapsed BOTH
trailing pre-`bgez` clusters *and* the first block's `a0 = &gfx` placement in a
single edit, 46 -> 30 words. Worth trying early on any function that emits the
same shape twice with shared temps.

## Finding 4 — the 0xC0 rectangle: a priority gap worth exactly one reference

The last large cluster was two instructions (`addiu $v0,$s1,0xC0; sll $a3,$v0,2`)
sitting after the two divides where ROM has them before. Giving every one of the
rect's ten arguments a named local — so RTL order equals source order — proves
the divmod expansion really is a barrier and the pair *does* move. It also
always flipped the `halfw`/`hgt` pair, because with `lrx` left in the argument
list it is register argument `a3`, which gcc sets after every stack argument, so
`halfw`'s last use sat past both divides and `halfw` outlived `hgt`.

`allocno_report.py` turns that from an argument into arithmetic. Both allocnos
carry 24 refs, so `global.c` `allocno_compare` reduces to
`floor_log2(nref) * nref / live_length`:

```
halfw : 4 * 24 * 10000 / 154 = 6233
hgt   : 4 * 24 * 10000 / 157 = 6114   -> halfw wins $s0, wrong
```

`hgt` needs `4 * n * 10000 / 157 > 6233`, i.e. `n >= 25` — **one extra
reference**, not a live-length change. Wrapping a single `hgt`-only statement in
a `do { } while (0)` supplies it: the macro-loop notes make the enclosed
reference count at loop depth 2.

```c
do {
  uly2 = (yc2 - hgt) << 2;
} while (0);
```

`hgt` goes 24 -> 25 refs, priority 6369 > 6233, takes `$s0`, and `lrx2` keeps
its early slot. 30 -> 2 words. Only this statement works: wrapping `lry2` gives
32, `dtdy2` gives 39 and costs an instruction, `lry2`+`dtdy2` 33, all three 33.

## Finding 5 — the preheader pair: delete the hoist rather than fight it

The last two words were `addiu $s5,$sp,0x40` (`&gfx`) and `addiu $s4,$zero,0x8`
(`off = 8`) emitted in the wrong order. Both registers were already correct, so
it was never allocation. Both insns are leaves with no in-block consumer, so
`INSN_PRIORITY` ties; both are independent of the last scheduled insn, so the
class test ties at 3; `sched.c` `rank_for_schedule` falls through to its last
line, `return INSN_LUID (tmp) - INSN_LUID (tmp2)` — emission order is RTL order.

I first concluded this was terminal, because `loop.c:1706` places a hoisted
invariant with `emit_insns_before (temp, loop_start)`, immediately before
`NOTE_INSN_LOOP_BEG`, so it necessarily *follows* any statement the source puts
before the loop. That reasoning is correct but it only closes one side of the
pair: it proves `off = 8` cannot be moved after the hoist. The other side —
removing the hoist so `&gfx` becomes ordinary source-order RTL *before*
`off = 8` — was never measured.

```c
i = 0;
gp = &gfx;          /* Gfx** gp; — an ordinary statement, not a hoist */
off = 8;
```

with both in-loop calls taking `gp`. The `-dL` dump is the proof rather than the
output: the `&gfx` movable **disappears from the movables list entirely**. Both
insns are then plain source RTL and the LUID tie-break yields ROM's order.

On its own this reads as catastrophic — 476 instructions, wrong frame, 473
words — and the dump again says why. Dropping the movable takes the loop from 62
to 61 real insns, so the `loop.c:1631` `li 1` hoist of Finding 1 fires again
(`Insn 428 ... moved to 1033`). It is compositional: one more dead RTL insn in
the loop restores 62. `yc = 0;` supplies it and **replaces** the older `y = 0;`
shim, so the final body carries exactly one dead store, not two.

Two lessons worth carrying: a negative verdict about a scheduler tie should be
stated over *both* insns of the pair, not just the one you tried to move; and a
lever that makes the output dramatically worse is not refuted until the dump
explains the regression, because the regression here was a separate, already
solved problem re-firing.

## Levers that did land

- `halfw = step * 34` **before** `hgt = span * step / 4`: ROM fills the two
  `mult`->`mflo` hazard slots with the halfw shifts, which only happens when
  halfw's RTL comes first. -2 nops.
- A `ulx` temp assigned **before** `yc = span / 4 + 0x86` at both trailing rect
  sites. Inlining `yc` into the args instead lets fold reassociate
  `span/4 + 0x86 - hgt` into `span/4 - (hgt - 0x86)` (+2 insns); keeping `yc` a
  statement but leaving `ulx` in the arg list drops ulx's three insns past the
  div-by-4's label.
- Respelling the x=0xC0 site's `lry` operand as a **second**
  `span / 4 + 0x86` (as its own variable, so fold cannot reassociate it). This
  fixes a span/off allocno swap: the two extra `span` refs raise its
  `floor_log2(nref)*nref/live_length` priority (global.c `allocno_compare`) from
  1111 past `off`'s 1272, so `span` takes `$s3` and `off` `$s4` as in ROM.
  Found by the permuter; the raw candidate carried the reassociation and cost an
  instruction.
- Per-region temps rather than per-role (Finding 3) — the single largest fix.
- The `do { } while (0)` reference bump on `uly2` (Finding 4).

## Permuter — and a false lead worth recording

Four runs with `--settings permuter_settings_main.toml`; base score
2275 -> 2000 -> 1475 -> 460 as the hand fixes landed. It produced two real
levers (the duplicated `span / 4 + 0x86` for the 0xC0 block, and the `uly`
statement).

On the 30-word base its best candidate scored 190 vs 460 by inlining `yc3` back
into the `lry` argument — and that candidate is **wrong**. It re-triggers the
fold reassociation `hgt + (span/4 + 0x86)` -> `(hgt + 0x86) + span/4` and costs
an instruction (475/474). asm-differ normalises registers and tolerates the
extra insn, so it scores the candidate well; a word-level positional oracle does
not. A permuter improvement is a hypothesis to re-measure, never a result.
Plateaued at 6062 iterations with no other candidate; stopped, not left running.
Re-imported once more on the 2-word body: base score 60, nothing in 2295
iterations. The crack came from the compiler dumps, not the search.

- **The reusable sentence: a permuter improvement is a hypothesis to re-measure,
  never a result.** This function produced a clean instance. asm-differ
  normalises registers and tolerates an extra instruction, so a candidate that
  is 475/474 can still score better than a correct 474/474 body. Score the
  candidate with a positional word oracle before adopting any of it.
