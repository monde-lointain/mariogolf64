body with identical registers ($f0 / $v0 / $v1).

## Root cause (fully traced, gcc-2.7.2 tools/cc/gcc)
- Assembler ruled OUT: KMC gas (binutils-2.6) does no general scheduling, only
  branch-delay swaps + nop insertion (`gas/config/tc-mips.c:1282-1288`,
  `:1523-1531`). The reorder is present in raw `gcc -S`. gcc is solely responsible.
- `movsf`(mov.s, type "move", no function unit) -> `mfc1` true-dep latency = **1**
  (`result_ready_cost` = 0, floored to 1 in `sched.c:1382-1385`). So mfc1 is
  issue-ready the slot right after mov.s; both mfc1 and the independent `li` are
  ready together. NOT a latency stall.
- `rank_for_schedule` (`sched.c:2385`): (1) INSN_PRIORITY, (2) class 1/2/3 vs
  last-scheduled, (3) INSN_LUID. The `.sched`/`.sched2` dumps show **all priorities
  = 1** (tie) and both class 3 (tie).
- **Decisive: `schedule_select` (`sched.c:2650-2680`).** Among equal-priority ready
  insns it front-loads the one with the largest `potential_hazard`. `mfc1`
  (INSN_LOAD_COPROC_DELAY, xfer result-latency 2) has a greater potential hazard
  than the `li`, so the scheduler moves `mfc1` and schedules it to absorb its
  hazard, placing the independent `li` into the mov.s->mfc1 slot. The sched2 dump
  says verbatim: `insn 10 has a greater potential hazard, now 10 29`
  (insn 10 = mfc1, insn 29 = li).
- **Pre-reload sched1 produced ROM order** (`mov.s; mfc1; li`); the post-reload
  sched2 hazard-fill is what swaps it. Base profile is plain `-O2` (both schedulers
  active; `flag_schedule_insns_after_reload=1` at optimize>=2, `toplev.c:3388/3398`;
  no `-fno-schedule-insns2`).
- Sequence (bottom-up sched2): scheduling `and`, `mfc1` (cost-2 xfer edge,
  `priority()` propagation `sched.c:1488`) is QUEUED 2 cycles (`sched.c:2603`) while
  `ori` goes ready; when `mfc1` re-enters the ready list the pending `li` is still
  there, `rank_for_schedule`'s LUID tiebreak would keep ROM order, but
  `schedule_select` (`sched.c:2615`) overrides it by `potential_hazard`
  (`sched.c:2656-2694`): `mfc1` on the memory unit with blockage 2 beats the
  unit-less `li` (hazard 0). The override only runs because `MAX_BLOCKAGE>1`
  (`sched.c:3733`). Independently reproduced/confirmed by a second gcc-source pass.

## Why no source lever (terminal)
The reorder fires whenever `mfc1` and an equal-priority independent insn are both
ready at that slot. To suppress it you must either (a) make the mask `li` NOT ready
there — impossible, `0x7FFFFFFF` is an inherently independent const load — or
(b) give `li`/`mfc1` different INSN_PRIORITY so they schedule in separate groups —
impossible at equal instruction count (both are priority 1; the path-length
difference washes out in this gcc's priority metric). `volatile s32 mask` DOES
force the order (const sinks before mov.s) but adds a stack frame + `lw` (wrong).
Permuter: 280s, no zero (a pure 2-insn reorder, not the exact-count-one-operand
shape the permuter cracks).
