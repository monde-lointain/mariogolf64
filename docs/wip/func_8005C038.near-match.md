# func_8005C038 -- record-table insert (S289 carry, 268/264)

Host `src/main/func_80059BA0.c`. Gate-rejected on its branch-likely tell by S287 and S288; S289
committed it as a declared crack-attempt slice and carried it with this verdict.

## Signature and semantics (re-derived from the `.s`, not inherited)

```c
void func_8005C038(s32 category, s32 score, s32 key, s32 arg3, s32 arg4);
```

Five arguments: `$a0`-`$a3` plus a fifth read from `0x70($sp)` (frame is `-0x60`, so that slot is the
caller's fifth outgoing word). The fifth lives in `$fp`, used as an ordinary callee-saved register for
the whole body -- not a frame pointer.

The save block returned by `func_8005AF50()` holds **four parallel `s32[6][3]` arrays**: key at
`0xD78`, score at `0xDC0`, and two payload words at `0xE08` and `0xE50` (stride `0x48` = 6*3*4). One
record is the same index into all four; `category` selects the 3-entry row (`category * 12`).
`func_8005AF80` in the same file initialises the `0xDC0` array to `-1`, and this function counts a
slot as live when its `0xDC0` word is `> 0`.

Body, in order:

1. `base = func_8005AF50()` -- first statement, before any argument handling.
2. `category` clamped to `[0, 5]`: `category &= ~category >> 31` (the ROM's `nor`/`sra`/`and`), then
   `if (category >= 6) category = 5;`.
3. `if (score < 0) return;` and `if (score > 108000) return;` -- 108000 = `0x1A5E0`.
4. `arg4` clamped to `[0, 3]` by the same two-step idiom.
5. `count` = number of the three `0xDC0` words that are `> 0`, accumulated branchlessly
   (`count += (0 < *p)`).
6. Pass 1 (`count != 0`): order the live entries by ascending score, copying record `j` down onto
   record `i` -- **not** a swap. Copy order is score, payload_a, key, payload_b.
7. Pass 2 (`count != 0`): scan each maximal run of equal keys, then sort that run by key again. The
   inner comparison is `key[m] < key[k]`, the same array the run was grouped by, so it can never
   fire; this is the ROM's own logic, faithfully transcribed, not a mis-read.
8. Pass 3 (`count > 0`): find the first `i` with `score < scores[i]`, or `score == scores[i] &&
   !(keys[i] < key)`. If `i < 3`, shift entries `[i, 2)` down one (when `i < 2`) and write the new
   record at `i`.
9. `count == 0` path: write the new record at index 0 with four displacement stores off one base.
10. `func_8005DF54(base, 1)`.

All three `count` tests jump to the same `count == 0` store block: gcc thread-jumps them, since
`count` is not modified in between.

## Residual: two parameters that will not colour (268 vs 264)

The attempt below is at the ROM's exact frame (`-0x60`, ten saved registers), reproduces every
control-flow edge, and reproduces both value-select `beql` clamps in step 2. Every one of the four
extra instructions is one of two opposed effects:

- **My build spills `score` (`$a1`) and `arg4` (the fifth argument) to their home slots** and reloads
  them at each use (about 13 instructions). The ROM keeps them in `$s6` and `$fp` for the whole body,
  which is also why the ROM's `arg4` clamp folds into `slti; beql; li` while mine, needing a store,
  emits `slti; bnez; sw; li; sw`. The branch-likely form is a *consequence* of the allocation, not an
  independent residual -- so the S263 value-select-branch-likely class does **not** apply here.
- **The ROM re-materialises `category * 12 + base` in the pass-3 scan and again in the insert block**
  (`sll`/`addu`/`sll`/`addu`, about 9 instructions) where my build keeps the pointer live in a
  register across the intervening loop.

Both are the same equilibrium: the ROM spends registers on the two parameters and pays to recompute
the row pointers; my build spends them on row pointers and pays to reload the parameters. The
function has ten callee-saved registers in both builds.

The knob is *how many of the four array base pointers are pointer locals in a given pass*. A local
becomes a `loop.c` induction pointer and holds a register; an offset expression off `row` gets
hoisted and merged instead, which removes the ROM's per-iteration address materialisation as well.
The ROM's own split, read off the `.s`, is: pass 1 keeps `scores` and `payload_a` as fixed bases
(`$s3`, `$s4`) and re-derives key/payload_b bases inside the outer loop; pass 2 keeps `keys` (`$s3`)
and spills the score base to `0x34($sp)`; pass 3's scan keeps `scores` and `keys`. Reproducing that
split exactly by choosing which arrays get locals over/under-shoots by 14 to 50 instructions -- the
two behaviours are not independently selectable from the source.

## Next step

Not a spelling problem: it is which allocnos win the ten callee-saved registers. The lead is
`global.c`'s `allocno_compare` priority (`floor_log2(n_refs) * n_refs / live_length`) -- `score` has
about six references over a ~270-instruction live range, so it ranks last, and the ROM's build had
one fewer competing loop pseudo. A `move_movables` / `global.c` compiler-source fan-out on *which
pass* gives up a base pointer is the right next move (the S280 play), not more source rewriting.

  s32 i;
  s32 j;
  s32 k;
  s32 m;

    category = 5;
  }
  if (score < 0) {
    return;
  }
  if (score > 108000) {
    return;

    arg4 = 3;

    i = 0;

      count += (0 < *p);
      p++;
      i++;

  }

    s32* row = (s32*)(category * 12 + (s32)base);
    s32* scores = (s32*)((u8*)row + 0xDC0);
    s32* payload_a = (s32*)((u8*)row + 0xE08);

        if (scores[j] < scores[i]) {

    }

    s32* scores = (s32*)((u8*)row + 0xDC0);
    s32* keys = (s32*)((u8*)row + 0xD78);

          break;

              scores[k] = scores[m];
              payload_a[k] = payload_a[m];
              keys[k] = keys[m];

            }

      }
