# func_8008E164 (lerp_s32) is a GCC nested function (S248 finding)

**Verdict:** `func_8008E164` is a GCC nested function — an orphaned out-of-line child.
The banked `volatile s32 unused = r;` form byte-matches but is a coincidental stand-in;
the faithful source is a nested function.

## Byte-for-byte proof
The clean nested child (NO volatile, NO uninitialized hack):
```c
int parent(int a1, int b1, float t1) {
    int child(int a, int b, float t) {
        return a * (1.0f - t) + b * t;
    }
    return child(a1, b1, t1);
}
```
compiled with the project toolchain (`tools/cc/gcc -B tools/cc/ -c -O2 -mips3 -mgp32
-mfp32 -G0`) emits `child.2` as these exact 20 words == ROM `func_8008E164`:
```
3c013f80 44810000 44862000 00000000 46040001 44841000 00000000 468010a0
46001082 44850000 00000000 46800020 46040002 46001080 27bdfff8 afa20000
4600100d 44020000 03e00008 27bd0008
```
`.frame $sp,8` / `.mask 0x0` (no callee-saves) matches too.

## Why the dead `sw $v0` is the static-chain home
- `STATIC_CHAIN_REGNUM = GP_REG_FIRST + 2` = `$2` = `$v0` (config/mips/mips.h:1310).
- A GCC nested function's prologue homes the incoming static chain to the stack
  (`subu sp,-8; sw $2,0(sp)`), even when the child never USES the chain. This child
  reads no parent variable, so the chain is homed but never reloaded -> the "dead"
  `sw $v0` + dead 8-byte frame. This is prologue codegen, not a DCE/frame coin.
- The parent passes the chain in the jal delay slot: `jal child.2 / addu $2,$sp,K`.

## Why it looks orphaned (no caller)
Exhaustive search of the whole ROM binary: ZERO `jal 0x8008E164` (bytes 0C 02 38 59)
and ZERO function-pointer words `80 08 E1 64`. The parent inlined its call(s) to the
child while GCC still emitted the out-of-line body -> a dead, uncalled nested body.
Its lexical parent is one of the still-`INCLUDE_ASM` siblings in `func_8008D100.c`.

## Sibling: func_80092E10 is the SAME family (chain-USED)
`func_80092E10` (carried this sprint as a "$v0-arg convention wall") is also a nested
function of a parent in this pack, but it USES its static chain: it reads its data via
`$v0` (= `&parent_local`). Its parent IS present and decompilable — the callers at
`0x800930F0` and `0x80093314` set `addiu $v0,$sp,0x10` (address of a parent local =
static chain), which persists to `jal func_80092E10` at `0x80093234` / `0x80093470`.
So func_80092E10 is NOT the [[func-80041e8c-v0-arg-convention-wall]]; it will match once
its parent is decompiled and it is written as a nested function accessing `sp+0x10`.

- Re-price `func_80092E10` from "$v0-arg wall" to "nested-function child, crack when
