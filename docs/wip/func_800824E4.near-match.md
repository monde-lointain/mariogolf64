# func_800824E4 near-match — S252, RE-DERIVED S258

`src/main/func_80080220.c` (0x800824E4, 0x50, 20 instrs). RGBA byte-packer.
**CARRIED**, now at 20/20 instructions with exactly ONE differing instruction
(one register operand).

## S252 verdict was based on wrong semantics

S252 read the function as taking THREE arguments with `b = arg2` on the negative
path, and called the residual a 2-insn transposition where "the delay-slot filler
never selects `$a2`". Re-reading the asm:

```
bnez  a0, .L4F8      ; if (shade != 0)
 li   a2, 0xFF       ; delay slot ALWAYS executes -> b = 0xFF on every path
 li   v1, 0xFF       ; zero path: g = 0xFF
 j    .L514
 li   v0, 0xFF       ;            r = 0xFF
.L4F8:
 blez a0, .L510      ; if (shade <= 0)
 addiu v1, a0, 0xFF  ; delay slot ALWAYS executes -> g = shade + 0xFF
 li   v0, 0xFF       ; positive path: r = 0xFF
 subu a2, v0, a0     ;                b = r - shade
 j    .L514
 move v1, a2         ;                g = b
.L510:
 move v0, v1         ; negative path: r = g
.L514: pack r<<24 | g<<16 | b<<8 | (alpha & 0xFF)
```

`$a2` is WRITTEN in the entry delay slot before any read, so the third argument
does not exist — the function takes `(shade, alpha)`. `b = 0xFF` is a shared
statement BEFORE the branch (that is why it lands in the delay slot: a normal
fill-from-before, not a scheduler coin), overwritten only on the positive path.

## Best reconstruction (S258, 20/20 instrs, 1 instruction differs)

```c
u32 func_800824E4(s32 shade, s32 alpha) {
  s32 r;
  s32 g;
  s32 b;

  b = 0xFF;
  if (shade == 0) {
    g = 0xFF;
    r = 0xFF;
  } else if (shade > 0) {
    r = 0xFF;
    b = r - shade;
    g = b;
  } else {
    g = shade + 0xFF;
    r = g;
  }

  return (r << 24) | (g << 16) | (b << 8) | (alpha & 0xFF);
}
```

A white-to-shade ramp: `shade == 0` gives opaque white; `shade > 0` darkens green
and blue by `shade`; `shade < 0` darkens red and green by `|shade|` and leaves
blue at full. Assignment ORDER inside the zero branch is load-bearing (`g` before
`r`, so `r`'s `li` is the one that lands in the `j` delay slot).

## Residual: ONE instruction

ROM `subu a2,v0,a0` (minuend = `r`'s fresh `li v0,0xFF`) vs build
`subu a2,a2,a0` (minuend = `b`'s pre-branch `0xFF`, still live in `a2`).

cse notices `r` and `b` hold the same constant and canonicalises the `r`
reference to the earlier member of the equivalence class (`b`/`$a2`); the ROM's
build did not. This is `#cse-make_regs_eqv-branch-fold`, NOT the S252
delay-slot-fill class. Source-invariant across every ordering tried:

| positive-branch spelling | result |
| ------------------------ | ------ |
| `r = 0xFF; b = r - shade; g = b;` | `subu a2,a2,a0` |
| `r = 0xFF; b = 0xFF - shade; g = b;` | `subu a2,a2,a0` |
| `r = 0xFF; g = r - shade; b = g;` | `subu a2,a2,a0` |
| `b = 0xFF - shade; g = b; r = 0xFF;` | `subu a2,a2,a0`, `li v0` sinks to the `j` slot |
| `g = 0xFF - shade; b = g; r = 0xFF;` | same |
| `b = 0xFF` moved into the zero and negative branches | 21 instrs (no hoist) |

Escalation: the permuter (a single-operand permutation on a 20-instruction leaf
is exactly its shape) or a `cse.c` `canon_reg`/equivalence-class dive to find
what keeps the two `0xFF` constants in separate classes.
