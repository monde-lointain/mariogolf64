# func_8007399C — near-match (S307)

`src/main/func_80071370.c`, `0x254` / **149 instructions**. Measured state: **149 of 149 at the
ROM's exact `-0x50` frame**, 84 differing lines in `tools/cmpfn.sh`, all of them one class —
entry-block emission order plus the register that holds the 5th parameter.

**The leaf cannot bank on its own, and that is a carve fact, not a codegen fact.** See the pool
section below before spending any time on the residual.

## Semantics (fully re-derived from the `.s`, confirmed by the call site)

Measures the on-screen extents of a stored glyph string. `func_800754BC` calls it as
`func_8007399C(id, size, &sp18, &sp1C, 0)`.

```c
void func_8007399C(s32 id, s32 size, s32* out_width, s32* out_height, s32 player);
```

- `id` indexes the glyph-run table `D_800E1C48` (`u16*`, the same `[t * 2 + 3]` idiom as
  `func_80071C9C`): `[id*2+2]` is the run's start, `[id*2+3]` its length.
- Each code unit is `D_800E1C48[D_80104FD0 + start + i]`. Both globals are re-read every
  iteration in the ROM, so they must be written as direct global references, not cached locals.
- `c < 0x100` is an ordinary glyph: `0xDE`/`0xDF` are skipped, `size == 0xC` adds the per-glyph
  advance `D_800C4390[c]`, anything else adds `size`.
- `c > 0x7FFF` is a control code dispatched through `jtbl_800D16D0` on `c - 0x8000`, 26 dense
  arms: 25 = newline (advance to the next of the three width slots, `total += 6 + size`), 15 =
  `sprintf` the player-name buffer `D_801321B0` and add `func_800738BC`'s measurement, 20-23 = read
  a per-player s32 at `D_8013F4DC[c - 0x8000]` offset by `player * 44`, `sprintf` it and add
  `func_80073BF0(buf) * size`, 0-10 and 12-14 = fixed `0xC`, the rest = no advance. Anything in
  `0x100..0x7FFF` is skipped.
- The three width slots start from the 12-byte zero template at `D_800D16C0`; the result is
  `max(w[0], w[1], w[2])`, stored to `*out_width` **twice** (once after each compare, which is what
  the ROM does), and the accumulated height to `*out_height`.

## The blocker: this is a pool-carve cohort, not a jtbl carve

`func_8007399C` regenerates `jtbl_800D16D0` (26 entries, `0xACAD0`..`0xACB38`, both edges
8-aligned). But `src/main/func_80071370.o` **already owns a `.rodata` carve**,
`[0xACBE0, .rodata, main/func_80071370]` (0x68 bytes = `func_800760CC`'s jump table), and an object
has one contiguous `.rodata`. Between the two sits `jtbl_800D1738` (`0xACB38`..`0xACBE0`, 42
entries), which belongs to the still-asm `func_800754BC`. So the object cannot supply `0xACAD0`
without also supplying everything up to `0xACBE0`.

**Unlock recipe (verified by construction, not yet executed):**

1. Bank `func_8007399C` **and** `func_800754BC` (0x350, 212 instructions, `fp=22`, the direct
   caller) in the same commit.
2. Replace `[0xACBE0, .rodata, main/func_80071370]` with `[0xACAD0, .rodata, main/func_80071370]`.
   The object's `.rodata` is then `0x178` = my jtbl (0x68) + `jtbl_800D1738` (0xA8) +
   `func_800760CC`'s existing table (0x68), and the ROM's order matches the file's definition order
   (`func_8007399C` line 342 < `func_800754BC` line 635 < `func_800760CC` line 641), so the three
   land in the right sequence.
3. The 16-byte zero template `D_800D16C0` at `0xACAC0` stays in the extracted blob: the body reads
   it as an extern struct copy (below), which emits no rodata. Do not spell the initialiser
   `s32 w[3] = {0, 0, 0}` — that emits a second template into the object and re-opens the carve
   one symbol earlier.
4. `func_80072A08` (owner of `jtbl_800D1658`, before `0xACAC0`) is **not** in the cohort; the carve
   starts after it.

Note `D_8013F4DC` is the symbol the source must name; splat prints the ROM's relocation as
`nuRDPOutputBuf + 0x251C` because gcc folds the `- 0x8000` element bias into the address
(`0x8013F4DC - 0x20000`). The `s32* pe` temp is load-bearing: without it the address adds
`row` before the symbol base and the arm's three instructions come out in the wrong order.

## The residual (84 cmpfn lines, one cause)

Everything reduces to **`player` living in `t0` instead of the ROM's `a3`**, plus the entry-block
order that goes with it:

| region | ROM | mine |
| --- | --- | --- |
| entry | `sw a3,0x24(sp)` first, then `lw a3,0x60(sp)`, then the callee-save block, then the template copy, then the `D_800E1C48` load | 5th-arg load first (into `t0`), `D_800E1C48` load second, `addiu s0,sp,0x10` third, the `a3` spill 18th, the template copy last |
| preheader | `move s2,zero` in the `beqz` delay slot; `wp = sp+0x10` last | `wp` computed in block 0 |
| jtbl base | `lui t0` | `lui t1` (t0 is taken by `player`) |
| epilogue | `lw t0,0x24(sp)` | `lw t1,0x24(sp)` |

`tools/allocno_report.py` gives `player` allocno 76 (`refs 4, len 26, priority 3076`) -> `t0`;
MIPS has no `REG_ALLOC_ORDER`, so allocation walks register numbers and `a3` (7) would win over `t0`
(8) if it were free across `player`'s range. `a3` is free in the RTL — `out_height`'s copy (insn 10)
kills it before the 5th-arg load (insn 12) — so the conflict comes from the schedule, not from the
allocno arithmetic.

`gcc -dS` on block 0 (`;; Function func_8007399C`, block 0, insns 4-57) prints the answer directly:

```
;; insn[  25]: priority = 1   (the movstr template copy)
;; insn[  31]: priority = 3   (the D_800E1C48 load)
```

`schedule_block` is bottom-up, so the priority-3 global load is chosen late and **emitted before**
the priority-1 block copy, which is the inversion against the ROM; the 5th-arg load (insn 12) and
the `wp` address (insn 19) ride to the top with it. The next probe is therefore either a source form
that raises the copy's priority (give it an in-block consumer) or one that lowers the global load's
(shorten its chain to the two `lhu`s).
