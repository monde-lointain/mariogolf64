## What the function does

tie flag: two equal minima set the result index `D_800C4144 = -1`. Then a weighted u16-table
redistribute over `D_8012D3CA` (14-byte rows = 7 u16 each): the winner row's first u16 gets
`+= D_800C4134 * (count-1)`, every other row's first u16 gets `-= D_800C4134`. `count = D_801B6090`,
`n = D_801B60BB` (s8). On a tie/no-winner, `D_800C4134 += n`; on a winner, `D_800C4134 = n`.

## The single residual divergence (base-register-vs-displacement, [#base-register-vs-displacement])
The array walk matches (byte-offset-cast lever landed). The residual is on the SCALAR globals:

| access | ROM (target) | my gcc |

| `n = D_801B60BB` | `lui a0;addiu a0,%lo; lb 0(a0)` (materialize full &sym into a0) | `lui v0; lb %lo(v0)` (fold %lo into load) |

Because a0 is consumed by the held base in the ROM, the whole loop's register coloring cascades:
ROM has counter=a2 / offset=a0 / best=a1; my build has counter=a0 / offset=a1 / best=a2. That coloring
swap is the bulk of the diff and is a direct consequence of the base-materialization decision, not
independently fixable.

## Root cause (gcc-2.7.2, cited)
`config/mips/mips.h` `GO_IF_LEGITIMATE_ADDRESS` **:2318-2349** accepts `(plus reg CONSTANT_ADDRESS)`
as a legitimate address: gcc folds `%lo(sym)` into the mem displacement over an index/base reg and
emits a fresh `lui %hi(sym)` per access. The in-source comment **mips.h:2325-2335** is explicit:
"the assembler can use $r1 to load just the high 16 bits ... whereas the compiler generates a 4
instruction sequence. On the other hand, **CSE is not as effective**. It would be a win to generate
the lui directly, but the MIPS assembler does not have syntax to generate the appropriate relocation."
So from faithful C referencing these as file-scope `D_` globals, gcc never CSE-shares the `%hi(sym)`
into one base register held across the nearby-symbol accesses; the ROM's opposite choice
(materialize full `&D_801B60BB`, reach `D_801B6090` via numeric `-0x2B` displacement, hold
`&D_801B6090` across the inner loop) is an addressing-mode + allocno-coloring artifact.

## Why no source form reaches it (probes run)
1. Plain globals (the faithful C above) → 10620, coloring counter=a0/offset=a1/best=a2.
2. `u8 *p=(u8*)&D_801B60BB; *(s8*)p` for n + `*(s32*)(p-0x2B)` for count → 11160; gcc constant-folds
   `&sym±k` back to a single symbol+addend relocated access (`lui a3;lw -43(a3)` with its OWN %hi),
   never sharing the base with the n load, and adds an extra beqz.
3. Struct-anchored at count (`u8 *h=(u8*)&D_801B6090; *(s8*)(h+0x2B)` n, `*(s32*)h` count) → 10620,
   same coloring; still one `lui` per access.

All three collapse `&sym±const` to an independent relocated load (the mips.h:2343-2349 folded path),
so the shared-numeric-displacement base is unreachable. Consistent with the hazard doc: the permuter
does not flip this (S210 ~9500 iters, no crack) — it is an addressing-mode/coloring decision, not a
source-reachable permutation. Score is far below the 0.97 permuter threshold and the divergence is not
permuter-reachable regardless.

**Verdict: WALL** (base-register-vs-displacement). Carry the faithful C above.

## S260 — the third access shape IS reachable (82/84)

`lw t0,-0x2B(a0)` needs the count and the flag to be the **same symbol**: cse's `use_related_value`
only relates offsets WITHIN one symbol, so two distinct `D_` symbols can never yield a negative
displacement off each other. Viewing the region as a struct through the existing array symbol does
produce the addressing:

```c
typedef struct { s32 count; u8 pad[0x27]; s8 flag; } RoundState;
#define ROUND (*(RoundState*)D_801B6090)
s8* flag = &ROUND.flag;   /* la a0,D_801B60BB ; lb 0(a0)     */
... ROUND.count ...       /* addiu t0,a0,-0x2B ; lw 0(t0)    */
```

**Remaining gap (2 instructions):** once both reads are on one symbol, cse merges the loop-bound read
into the entry guard's read and the preheader `lw t0,-0x2B(a0)` disappears (82/84). The ROM keeps both
loads with only the constant-address `D_800C4144 = -1` store between them, and that store cannot
invalidate the first: `note_mem_written` (cse.c:7564) sets `nonscalar` only when the store's address
VARIES, and `invalidate_memory` (cse.c:7715) purges `in_struct` entries only for a nonscalar write.

Tried and rejected: array-form guard + struct-form bound (same address, still merged); caching the
bound in a preheader local (merges into a `move`); routing the `D_800C4144` store through a pointer
local to make its address vary (expand folds it back to the symbol before cse records the write).

So the wall is now ONE mechanism, not an addressing mystery: something has to keep cse from forwarding
the guard's load to the preheader. Candidates for the next attempt: a store with a genuinely varying
address between them (an array element with a runtime index that the ROM also has), or a source shape
that gives the preheader block a second predecessor (memory `ifelse-not-ternary-cse-reset`).

## S261 — the wall is a MUTUAL EXCLUSION between the addressing form and value-holding (terminal for source)

The ROM's preheader load `lw t0,-0x2B(a0)` needs BOTH properties at once, and the two source
mechanisms that each deliver one property DISABLE the other. Three 84/84-or-82 forms, measured:

| form | count spelling | addressing | value | count |
| ---- | -------------- | ---------- | ----- | ----- |
| A | `while (i != ROUND.count)` (struct-view, in loop test) | **a0-relative** `addiu t0,t1,-0x2B` ✓ | **re-read each iter** `lw v0,0(t0)` ✗ | 84 |
| B | `count = *(s32*)((u8*)flag - 0x2B)` (pointer arith, hoisted) | **fresh** `lui t0;lw -0x2B(t0)` ✗ | **held** ✓ | 84 |
| C | `count = ROUND.count` (struct-view, hoisted local) | a0-relative | **merged into the guard's v1 load** → preheader load gone ✗ | 82 |

The ROM wants a0-relative addressing (property of A/C) AND a held value (property of B). The conflict
is structural, not a spelling gap:

- **a0-relative addressing requires the struct/related-value form** (`&ROUND.count` off `&ROUND.flag`),
  which is a `MEM_IN_STRUCT_P` may-alias reference. gcc's loop-invariant motion cannot prove the
  in-loop stores (`D_800C4144 = i`) do not alias a may-alias struct field, so it **cannot hoist the
  value** → the value is re-read every iteration (form A). Hoisting it to a preheader local instead
  (form C) places the read adjacent to the guard in the same extended BB, where cse forwards the
  guard's already-loaded value (constant-pointer fold: cse knows `flag == &D_801B60BB`, so
  `plus(flag,-0x2B)` folds to `symbol D_801B6090`, identical to the guard's `D_801B6090[0]`) → merge.
- **A held value requires a non-may-alias (plain-symbol) read** so gcc can prove no-alias and hoist it,
  but a plain read of `D_801B6090` folds `flag - 0x2B` to the constant symbol and materializes its own
  `%hi` — the fresh `lui`, not the reused flag base (form B).

So `{a0-relative address}` ⟹ mem-in-struct ⟹ `{re-read OR merge}`, and `{held value}` ⟹ plain read ⟹
`{fresh lui}`. No source form yields `{a0-relative AND held AND unmerged}` together. This is
distinct from — and stronger than — the earlier "keep cse from forwarding" framing: even a form that
does NOT forward (A) fails, because the same mem-in-struct property that stops the forward also stops
the hoist. **Verdict: TERMINAL for source.** The permuter cannot help (form A/B are exact-count but the
divergence is an addressing-mode + load-placement choice, not a register permutation; form C is 2
short). Carry form A (84/84, cleanest — the residual is one held-vs-reread load).
