Root cause: **global.c:594-601 `allocno_compare`**, priority =
`floor_log2(n_refs)*n_refs / live_length * 10000 * size`, ties broken by allocno index
(creation/first-mention order). The reference permutation is *non-monotonic* in the obvious
source factors — it ranks `row` above `idx` and `seg` above `col`, i.e. the OUTER loop var
above the higher-n_refs inner var. That inversion is only possible because the inner var's
`live_length` (allocno_live_length = MAX reg_live_length over the allocno, global.c:422-423)
is inflated by spanning the whole function / whole nest, dragging its ratio below the outer
var's. Consequences:
- The permutation is sensitive to whole-function live_length (instruction counts across ALL
  mode blocks), so any single-block source edit (extra biv ref for a floor_log2 jump,
  live-range extension, giv conversion) shifts multiple allocnos' live_lengths at once and
  cannot flip one comparison in isolation. Two independent permutation groups would have to
  land simultaneously and consistently.
- Class 2 is dispositive on its own: reaching byte-exact requires FORCING gcc-2.7.2 to
  re-materialize a loop-invariant `li` it chose to hoist while a register (t9) is free —
  i.e. de-optimizing. No source construct reliably suppresses loop.c move_movables const
  hoisting; and adding the 5 missing reloads by hand is not expressible in C.
