# func_8007955C near-match (S244 carry)

`src/main/func_80078910.c` particle-spawn family, 3rd sibling. **Fully RE'd; every store value +
offset + the two calls match. Residual = a gcc-2.7.2 sched.c SCHEDULE-ORDER coin** (~19 differing rows

scheduler coin (companion to S243 `sched-class-tiebreak-order-coin`).

## What it does
Spawns a particle into the first free `particle_array` slot (`unk_3A == -1`, recompute base
`&particle_array[i]` via `sll i,6`+`addu`), then builds a float RTS matrix on the stack and packs it
into the fixed-point `Mtx` array `D_FD8F0[unk_3C]`:
- `unk_00/04/08` = `(f32)arg0[0..2] * (1/1024)` (fixed->float position).
- `unk_3A=12`, `unk_3B=0`, `unk_3C = frame_counter` (byte); `unk_0C/10/14=0`;
  `unk_28=95.0`, `unk_2C=-2.0`, `unk_30=1.0`, `unk_34=0.1`.
- `frame_counter = (frame_counter + 1) % 40` (signed `/40` magic `0x66666667` + `>>4`; frame_counter
  @0x800C52B4, treat as s32 for the signed div).
- `translate[3] = {unk_00,unk_04,unk_08}` (reloaded from the struct), `rotate[3]={0,0,0}`,
  `scale[3]={unk_30,unk_30,unk_30}` (three reloads of the just-stored 1.0 — gcc can't CSE across the
  possibly-aliasing sp-buffer stores).
- `mtx_from_rts(mf, rotate, translate, scale)` then `convert_and_pack_floats_to_fixed(mf,
  &D_FD8F0[unk_3C])`.

## Cracks already landed (structural, all HELD)
- **Stack layout**: decl order `translate, rotate, scale, mf` places them at sp+0x10/0x20/0x30/0x40
  (frame 0x90, `s1=&mf` callee-saved across both calls) — byte-exact prologue.
- **Recompute base** `Particle* p = &particle_array[i]` (S184) = the ROM's `sll i,6`+`addu s0` element
  pointer (this sibling uses recompute, NOT the running-pointer of 79940/79A08).
- **Const-store interleave** (`unk_28=95` moved adjacent to `unk_00`) drops 19->15 rows but INVERTS the
  FP-reg assignment (unk_00 value -> f2 instead of f0), so the natural order is the cleaner near-match.

## Residual (terminal for hand-source)
Two coupled symptoms, both pure schedule:
1. Target STORES `unk_00` early (right after its `mul.s`, before the const setup) so it can reload it
   (`lwc1 f10`) for `translate[0]`; my build defers the store past the const block.
2. FP-const reg ROTATION: target 95->$f2, -2->$f4, 1->$f6, 0.1->$f8 (first-materialized = f2); mine
   rotates them (1/0.1 grab f2/f4) because gcc schedules the const `mtc1`s at a different point.
The const materialization fills the `mul.s`->`swc1` load-latency gap in the ROM; source store-order
reshuffles (natural / const-interleave / unk_08-temp-split) move the row count 15<->19 but do not
reproduce the exact fill. Permuter-responsive in principle (S243 74230 precedent) but < 0.97 gate and
not attempted this sprint.
