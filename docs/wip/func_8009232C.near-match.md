# func_8009232C -- near-match carry (S302)

`src/main/func_8008D100.c`, 0xAE4 / 697 instructions, jal-free, FP-free, branch-likely-free.
Reconstructed to **698 instructions with an exact `-0x38` frame** on the same day it was opened.
Every display-list command word was resolved against `include/libultra/PR/gbi.h`; the residual is a
single register-allocation decision that permutes the whole body.

## What the function is

A snapshot-replay display-list emitter, the fourth member of the `func_8008D100.c` capture/replay
family (`capture_frame_snapshot`, `emit_screen_transition_overlay`,
`emit_snapshot_spiral_wipe_dl`). Signature `void func_8009232C(Gfx** gfxp)`.

Guarded by `D_800C5EE4 > 0` (the shared countdown; `func_800959F8` returns `D_800C5EE4 < 1`). It
emits a nine-packet mode preamble, then dispatches on `D_800C5EE8` when `D_800C7304 == 0`:

| `D_800C5EE8` | body | tail |
| --- | --- | --- |
| 6 | PipeSync, `G_RM_OPA_SURF`, prim 127/127/127/255 | falls into the common tail |
| 1 or 9 | PipeSync, `G_RM_CLD_SURF`, prim 255/255/255/`D_800C5EE4` | falls into the common tail |
| 7 | prim 255/255/255/95, `G_RM_CLD_SURF`, `G_CC_MODULATEI_PRIM`, then a 38-iteration `gDPLoadTile` strip replay off the LIVE framebuffer `D_800FED10` | returns, no countdown decrement |
| 8 or 10 | `G_RM_OPA_SURF`, `G_CC_DECALRGB`, prim white, then a 38-iteration two-rectangle curtain wipe off `D_800C5EE0` | `D_800C5EE4 -= 12`, returns |
| anything else, or `D_800C7304 != 0` | the common tail | |

Common tail: `G_CC_MODULATEI_PRIM`, PipeSync, a `y = 8; y < 232; y += 6` block replay, then
`D_800C5EE4 -= (D_800C5EE8 == 9) ? 24 : 12` and, if that goes negative,
`D_800C7308 = (D_800C7308 + 1) % 8`.

The three loops all replay the 304x224 capture six scanlines at a time over 38 strips, the last one
being the two-line remainder -- the same shape `emit_screen_transition_overlay` uses. Loop A
(`mode == 7`) uses `gDPLoadTile` against a 320-wide `gDPSetTextureImage`; loops B and C use
`gDPLoadTextureBlock` on the first iteration and a bare
`SetTextureImage / LoadSync / LoadBlock / PipeSync` reload on every later one, gated by a
function-scope `first` flag that loops B and C share (`$s0`, zeroed at 0x80092374).

The mode-8 curtain emits two `gSPScisTextureRectangle`s per row: a left one from x=8 to
x=`D_800C5EE4` sampling s=`(160 - D_800C5EE4) << 5`, and a right one from x=`320 - D_800C5EE4` to
x=312 sampling s=`152 << 5` (152 = the 304-wide capture's midpoint).

| lever | effect |
| --- | --- |
| walking `addr` variable per loop instead of `src + i * stride` | removes a per-iteration `move`; 699 -> 698 |

## Residual: one hoist and one spill

`venv/bin/python3 tools/loop_window.py src/main/func_8008D100.c func_8009232C` and
`tools/allocno_report.py` localise the whole 1265-row diff to two coupled decisions in loop B
(255 real insns, threshold 122):

1. **`0xF3000000` is hoisted in my build and materialised in-body in the ROM.** My loop B moves
   `{FD100000, -8, E6000000, F3000000, 0700001B, E7000000, E1000000, F1000000, 04000400}`; of these
   only `F3000000` actually keeps a hard register (`$s8`), the rest are rematerialised. The ROM's
   loop-B preheader holds exactly five: `0700001B ($s6)`, `E7000000 ($s4)`, `E1000000 ($fp)`,
   `F1000000 ($s7)`, `04000400 ($s5)`. Under `move_movables` (`loop.c:1631`) `F3000000` and
   `0700001B` are indistinguishable in my build (both `savings 2`, `lifetime 2`, and `F3000000` is
   scanned FIRST, so it can only be more likely to move), yet the ROM moves the second and not the
   first. That is only consistent with the ROM's loop-B RTL having different `savings`/`lifetime`
   for the two, which no spelling tried this sprint reproduced.
2. **`src` is a memory-homed local in the ROM and a register in mine.** The ROM stores
   `(u32)D_800C5EE0` to `0xC($sp)` at entry and reloads it in the loop-B and loop-C preheaders
   (`lw $t6,0xC($sp)` / `lw $a3,0xC($sp)`). `allocno_report.py` puts my `src` allocno at priority
   230 (`refs 3`, `live_length 130`) against the loop constants at 220-228 -- it wins its register by
   about 7 units of live length. With `$s8` already taken by the extra hoist there is no callee-saved
   scratch left, so `0x04000400` is spilled to `0xC($sp)` and reloaded twice per loop-B iteration
   instead.

Fixing either one alone is not obviously enough: killing the hoist frees a register that `src` would
then still win. The actionable next step is the priority window -- lengthen `src`'s live range past
136 units, or find the spelling that gives `0700001B` a longer lifetime than `F3000000`.
