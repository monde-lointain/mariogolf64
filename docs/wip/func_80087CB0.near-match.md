## The S258 crack chain (what moved 1580 -> 345)

The ROM computes every coordinate as `(GLOBAL + CONST) + array_elem`, keeping
ONE load of each `D_800C54Cx` scalar and RE-LOADING the `D_800E21xx` array
element at each use; the constant lands on the global (`addiu vN,aN,C`, and the
second x use is a destructive `addiu t0,t0,0x108`). My builds put the constant
on the array element instead (`addiu vN,vN,C; addu vN,globreg,vN`), which costs
one extra add on the x side (3 elem re-loads means 3 constants) and permutes the
registers.

Root cause is `fold-const.c:3685 associate` in gcc-2.7.2 (**not** scheduling and
**not** regalloc):

- `split_tree(arg0)` rewrites `(VAR + CON) + ARG1` to `VAR + (ARG1 + CON)` —
  it MOVES the constant OFF the global onto the other operand
  (`fold-const.c:3722-3736`).
- `split_tree(arg1)` (`fold-const.c:3759`) rewrites `ARG0 + (CON + VAR)` to
  `(ARG0 + CON) + VAR` — it moves the constant ONTO `arg0`.

So the association is decided by WHICH SIDE the parenthesised constant sits on:

1. **`GLOBAL + (elem + CONST)` reproduces the ROM's `(GLOBAL + CONST) + elem`.**
   The arg1 split rewrites it to exactly the ROM form, while the natural
   spelling `GLOBAL + CONST + elem` is rewritten the WRONG way by the arg0
   split. This one re-spelling on the two y coordinates was worth 98 -> 66 diff
   rows. Generalisation: *to pin a constant onto a global in a 3-term sum, write
   the constant inside parentheses on the OTHER operand.*
2. **A base held in a local temp is immune** (no constant is left in the
   expression to reassociate), so `s32 xl = GLOBAL + CONST;` then `(elem + xl)`
   also gives the ROM form — plus the ROM's shared/destructive `addiu` when the
   base has more than one use. Used for the two x coordinates.
3. **But a temp is only correct where the ROM keeps the base live.** The ROM
   keeps the x base (`t0`) live into the s-clip (same BB, before the `bgezl`)
   but RE-LOADS `D_800C54C4`/`D_800E21A8`/`D_800C5AD0` for the t-clip (a
   separate BB after the branch, where cse's table is reset). A temp for the y
   base therefore comes out 3 instrs SHORT (249 instrs). x = temp, y = inline is
   the only split that yields the exact 252.
4. `extern s32 D_800C54C8[]` + `[0]` (MEM_IN_STRUCT_P) keeps the load from being
   hoisted ~22 instrs early by sched1, matching the ROM's late load.

Measured variants (all at 252 instrs unless noted): x temp + y natural = 98 rows;
x temp + y arg1-split = **66 rows**; both temps = 249 instrs; both inline = 253
instrs; `(D_800C54C4 + 0xAE) + elem + D_800C5AD0` grouping = 136 rows (it also
breaks the shared `&D_800E21A8` address base); a single `c8 = D_800C54C8[0]`
load-temp + arg1-split for x = 96 rows.

## Residual (S258)

Pure register permutation plus one scheduling tie; the instruction shapes are
now identical:

- ROM emits `lw v1,0(t1)` (the `D_800E2190` element) BEFORE
  `lui t0,%hi(D_800C54C8); lw t0,%lo(...)`; my build emits the two loads in the
  opposite order. Both are sched1-hoisted to the same point, so the order is a
  LUID (source emission order) tie — and the `D_800C54C8` load is emitted first
  because it comes from the `xl`/`xh` temp initialisers, which must precede the
  macro call. Every attempt to defer it (inline arg1-split form, a single
  `c8 = D_800C54C8[0]` load temp, scalar retype) either restores the early hoist
  or breaks the shared `&D_800E2190` address base.
- Downstream, `D_800C54C4`'s value lands in `a0` where the ROM uses `a2`, with
  the clamp scratch swapped to match (`a0` <-> `a2` throughout).

## Levers confirmed here (reusable)

1. **`gSPScisTextureRectangle` is the macro** for any MG64 texrect whose
   coordinates carry a branchless `sll 18/sra 16/nor/sra 31/and/andi 0xffc`
   clamp plus an asymmetric `bgezl`(s16 x)/`bgez`(s32 y) s/t clip with
   `slti 1; negu; and; negu`. Hand-reconstructing those clamps never converges.
   `gbi.h:4498`. Same family: `func_80088890` (BANKED S258 with this macro) and
   `func_800842C0`/`func_80088A90`.
2. **if/else, not a ternary**, when the ROM RE-LOADS a global that was just
   stored in both arms: the two stores cross-jump-merge after the join and the
   cse table reset forces the reload (a ternary keeps the value in a pseudo and
   folds the following DL block onto the previous block's base register).
3. **`extern u8 G[]` + `G[0]`** (MEM_IN_STRUCT_P) stops sched1 hoisting the load
   above varying-address DL stores.
4. **The fold arg0/arg1 split rule above** — the general lever for steering
   which operand of a 3-term sum carries the constant.
